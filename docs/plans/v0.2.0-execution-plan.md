# HivePlane v0.2.0 — Execution Plan

> Status: draft. Working plan for the v0.2.0 build — the Complete Fleet OS and final big release.

## Objective

Ship the Complete Fleet OS: the fleet runs itself (triggers, pipelines, GitOps reconciliation), defends itself (drift, injection, policy, kill switches), explains itself (cost/ROI, reporting), and scales itself (tenancy, distributed workers, Helm). Absorbs all former v0.3.0/v0.4.0 scope. This is the last big release; afterwards the project enters maintenance mode.

## Sequencing

Follow the [WBS v0.2.0](../wbs/v0.2.0/wbs-v0.2.0-index.md) in order, grouped into phases with review checkpoints:

| Phase | Weeks | Parts | Milestones | Theme |
|-------|-------|-------|------------|-------|
| 0 — Foundation | 1-2 | 1 | M25-M26 | Data models + GitOps reconciliation |
| 1 — Autonomy | 3-5 | 2-3 | M27-M30 | Triggers + multi-agent orchestration |
| 2 — Immune system | 6-8 | 4-5 | M31-M34 | Runtime v2, promotion gate, drift/quarantine |
| 3 — Learning & rollout | 9-11 | 6-7 | M35-M38 | Provenance, feedback→corpus, shadow/canary |
| 4 — Defense & health | 12-14 | 8-10 | M39-M44 | Policy, guards, SLO, probes, MCP v2 |
| 5 — Fleet execution & cost | 15-17 | 11-13 | M45-M50 | Secrets, workers, scheduling/HA, cost/ROI |
| 6 — Operator & API | 18-20 | 14-17 | M51-M58 | Delivery, UI v2, CLI/copilot, API/SDK, tenancy |
| 7 — Distribution & release | 21-24 | 18-19 | M59-M62 | Helm, replay, field test, release |

**Review checkpoint at each phase boundary:** exit gates green, a demo of the phase's capability, and a go/no-go on the next phase. Roughly 4-5 months at the v0.1.0 pace; field-test findings (Phase 7) can extend it.

## First Step

Prove the extended loop end-to-end in miniature before building breadth:

1. register a workload on the new schema (M25)
2. reconcile desired state from git (M26)
3. start a run from a webhook trigger (M27-M28)
4. chain two workloads in a pipeline (M29)
5. gate promotion on re-certification and quarantine a seeded drift (M32-M34)
6. fan out the result to Slack (M51)
7. see the whole story in the UI (M52)

**Why this first:** it exercises every integration seam the rest of the release depends on — schema, reconciliation, triggers, pipelines, the immune system, delivery, and the operator surface — with real workloads instead of speculative architecture.

## Parallelization

The critical path is Phase 0 → 2 → 3 → 7 (foundation → immune system → learning → release). After Phase 0, these tracks can run concurrently, subject to review capacity:

- Triggers (Part 2) · Orchestration (Part 3) · Defense (Part 8) · Cost (Part 13) · Delivery/UI (Part 14) · Corpus/API (Part 16) · Reporting/Tenancy (Part 17)

**Recommendation:** at most two parallel tracks, one milestone at a time each. The exit-gate discipline (below) is the bottleneck, not the code.

## Working Agreements

- one milestone at a time per track; exit gate before advancing
- every milestone exit requires: all tests pass, coverage > 95%, ruff clean, mypy strict clean, docs updated, all issues closed, changes committed and pushed
- security-critical parts (secrets, isolation, provenance/signing, RBAC, tenancy) require adversarial tests and a dedicated review before exit
- every feature maps to at least one field-test scenario before release; no unreachable release gate
- the certified control loop and the immune system ship before breadth UI
- adapters stay behind the contract; nothing framework-specific leaks into core
- experimental/stretch scope (A2A, federation) stays behind a feature flag and never blocks the release
- no milestone closes with a red gate; if a gate is red, the milestone is in progress

## Load-Shed Order

If the schedule slips, cut in this order (last out): federation → demo profile → global search → onboarding wizard. **Crown jewels that must never be cut:** pipelines + canary, GitOps reconciliation, context budgets, `ask`.
